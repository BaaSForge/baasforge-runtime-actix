# Runtime persistence gaps

> write a paragraph about the issue which we already have:
> 1. actor alarams are only on redis, if redis crashes or restarts, we will loose all alarms data
> 2. workflow is using redis persistence with the issues you just mentioned, it must be re-designed to match enterprise companies
> 3. all other units (current one or later ones) must have a proper persisntence to survive crashes, we must later analyze other platforms to find out how they do this so we will follow too

Today’s runtime data is not uniformly durable across unit types. **Actor alarms** live only in Actor Redis (global and per-actor sorted sets): if that Redis process crashes, is wiped, or is replaced with an empty instance, **all scheduled alarms are lost** until user code re-arms them—there is no platform-level catalog of pending fires that survives Redis volume loss. **Workflows** already lean on Redis persistence (AOF/RDB and replication) for hot execution state, which is workable for many deployments but carries the usual enterprise caveats—bounded RPO depending on `appendfsync`, snapshot gaps, replication lag on failover, operational risk from bad restores or `FLUSHALL`, and a weaker story than systems that keep **durable history** in a transactional store (the pattern serious orchestration products use). That gap means workflow durability should be **revisited** so it matches what enterprise buyers expect: explicit RPO/RTO, auditable history, and failure modes that do not depend on a single best-effort Redis tier alone. **All other units**—HTTP-adjacent caches, queue workers, future actors/streams/triggers—should eventually follow a **single discipline**: every class of runtime-owned data (timers, mailboxes, locks, step journals, dedupe keys) must declare whether it is **ephemeral**, **Redis-persisted with documented RPO**, or **backed by a durable store**, and we should **benchmark major platforms** (hosted workflow vendors, Orleans-style reminder storage, queue SaaS) so our defaults and ops story align with industry practice rather than ad hoc Redis assumptions.
